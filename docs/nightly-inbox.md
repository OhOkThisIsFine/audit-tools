## `sol-1` — Leg 2 has failed two nights running on a masked rate limit — the lane throws away the error that names its own retry-after

*Recurring-problem solutions · open 1 night · `scripts/shared/triage-backlog.mjs`*

### In plain terms

Leg 2 of this routine checks every backlog entry against the code to find entries whose work already shipped. It does that through a helper script that asks a cheap model to classify one entry at a time. Tonight that script failed on 94 of 106 entries, and every single failure recorded the same message: "finish_reason=undefined". That message says nothing, so the natural reading is that the model is broken — which is why three different models were tried, each converting only a handful more entries. Adding one line to print the actual response body gave the real answer immediately: the provider was returning a plain rate-limit error stating its own limit (8000 tokens per minute), how much was used, and exactly how long to wait ("Please try again in 20.4525s"). The script throws all of that away, because it only looks for a field that a rate-limit response does not contain. It also never waits and retries. The fix does not need new machinery: this repo already has a shared quota-error parser that reads exactly these retry-after fields. The script hand-rolls a worse version of something it could import.

## `sol-3` — A probe path that does not exist reads exactly like a premise that vanished — 44% of tonight’s leg-2 probes, and 20 of its 27 "already done" stamps

*Recurring-problem solutions · open 1 night · `scripts/nightly/items.mjs`*

### In plain terms

Backlog and nightly items carry "premise probes": a file plus a literal string quoted from it, so the tool can mechanically check whether the thing an item complains about is still in the code. If every quoted string has disappeared, the item is treated as done and closed automatically. The bug is in how "disappeared" is decided. The checker tries to read the file; if the file is not there at all, it records the same result as if the file were there and simply no longer contained the text. Those are completely different facts — the second means the work shipped, the first means somebody wrote the path wrong — and collapsing them turns a typo into the strongest possible claim, "this is already finished". This is not hypothetical. Tonight’s leg-2 pass asks a model to emit those probes, and that model cannot see the repository, so it writes bare filenames like "serve.mjs" instead of "scripts/nightly/serve.mjs". Of the probes it produced, 44% named a path that does not resolve, and 20 of the 27 rows stamped "premise gone" rest on at least one of them. Every one of those files genuinely exists, just at a real path. There is already a guard for this on the other consumer — the nightly items file refuses to save an item whose probes do not currently pass — but the backlog-triage path has no such check, so the bad probes there become the most confident verdict in the file, and that verdict is the input to deleting backlog entries. The fix is to stop collapsing the two absences: report "file missing" separately from "text missing", and never let a missing file contribute to an automatic close.

### The question

Approve splitting probe absence into "file not found" versus "fragment not found" in evaluateProbes, so only a genuine fragment-absence can auto-close an item, and a malformed probe degrades to no-signal instead of to "shipped"?

### ⤺ You asked back

> Would the best solution not to be to look at diffs? Git records tracked file history, and we can compare old to new versions to see whether something was fixed.

**Answer:**

Yes — that is better than what I proposed, and it subsumes it. I was going to split one bit (file-missing) from another (text-missing); git answers the sharper question directly, with evidence instead of inference.

Two things it gives that my version cannot:
- 'Was this path EVER real?' — 'git log --all --full-history -- <path>' returning empty is a definitive bad-probe verdict. My proposal could only say 'not there now', which is exactly the ambiguity that produced the 44% noise.
- 'Which commit removed this text?' — 'git log -S<literal> -- <path>' names the commit. An auto-close then cites the commit that closed it, so the claim is checkable later instead of being a silent inference.

It also retires a trade-off the item contract currently concedes outright: 'a rename mis-closes'. Git's rename detection follows the file, so that concession stops being necessary rather than being documented.

Two caveats worth building in from the start:
- A shallow clone has no history to query, so the check must FAIL OPEN — unknown means the item stays open and is surfaced, never auto-closed. An auto-close that depends on clone depth would be a new false-green of exactly the kind this is meant to remove.
- It does not solve semantic staleness: if the quoted text was rewritten but the underlying bug remains, git says 'removed' and the item still closes wrongly. Same limit as today, just worth not overclaiming.

So: adopt the git-history version instead of the state split, fail open on missing history. If you want, I will respec sol-3 that way and bring it back rather than treating this as approval to build it.
