## Why three carry no patch

The same reason last run gave for P54, P55 and P57: in each the owner is being
asked WHICH FORM, and the candidate forms share no code, so a patch written
before that answer would be discarded. Each proposal states its forms explicitly
under *The open choice*. P58's form is settled — adopt the machine's existing
shim resolver — so it carries its patch and its measured RED-AT.

## The thread through P58 and P59

Both are the same honesty property at different points of one lane's life. P58 is
about lane PROBING: a probe that could not start reports the lane dead. P59 is
about lane RETURN: a process that terminated without producing anything returns
that nothing as an answer. In both cases a defect in the machinery is presented
in the vocabulary of a real result, which is the shape that costs the most to
diagnose because it never looks like a failure.

P58 was found by this run rather than read out of a record: the session opened
with a guard reporting the Codex lane down, and the lane answered a probe in
under a second.

P62 belongs to the same family one layer down, and the pair is the finding. P58
is a child process that cannot be LAUNCHED, because a bare name resolves to an
npm `.cmd` shim Node cannot execute. P62 is a child process that launches and
then cannot READ its argument, because a bare name resolved to the one `tar` on
the box that parses `C:` as a hostname. Both assembled an argv without asking
what platform it runs on. Both were invisible until measured on Windows. Two
found independently in one night is the argument for P62's third option — route
the question through `resolveExecArgv` once, rather than answering it again at
each call site.
