THE TRIGGER IS PATH ORDER, AND IT WAS MEASURED DIRECTLY. Same machine, same
session, one archive, two PATHs (.audit-tools/nightly/tar-probe.mjs):

    inherited PATH:
      flavour: tar (GNU tar) 1.35
      extract status: 128
      stderr: tar: Cannot connect to C: resolve failed
    System32 first:
      flavour: bsdtar 3.8.4 - libarchive 3.8.4
      extract status: 0

`which -a tar` → /usr/bin/tar, /bin/tar, /usr/bin/tar, /c/Windows/system32/tar.
Git Bash's GNU tar resolves FIRST in this session, ahead of the drive-letter-safe
system bsdtar. GNU tar parses a leading `host:` as a remote machine, so an
archive path beginning `C:\` is never opened as a file.

SO THE DEFECT IS LATENT, NOT DORMANT-THEN-BROKEN. The call site names a bare
`tar` and inherits whichever one the launching environment happens to put first.
A run launched from PowerShell or from a plain Windows shell gets bsdtar and
passes; a run launched from anything that puts Git Bash first gets GNU tar and
fails. Nothing in the tree changed between the green and the red — only the
environment the suite was launched from.

That is a stronger argument for the fix than a regression would have been: a
green suite here is currently a property of the launcher, not of the code.

WHY LINUX CI NEVER SEES IT: on Linux the archive path carries no drive letter, so
GNU tar reads it as an ordinary path.
